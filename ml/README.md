# RMUC 对局预测实验

当前网页默认使用“局势条件目标分类 + 英雄真实发弹阵位排序 + 真实热图候选 + 多峰时序 Transformer 分布”的混合策略。Transformer 给定最近 5 秒全场状态，为每个预测时刻输出 8 个带概率和尺度的连续位置分量；引擎用完整分布重排真实热图候选，不把多个合理去向平均成一个不存在的空地点。英雄排序器另用真实 42mm 发弹选择监督，旧单点 Transformer 和 MLP 检查点仍保留作可复现基线。

模型同时输出 `1 / 3 / 5 / 10 / 15` 秒后的位置。输入包含：

- 双方 12 辆移动机器人最近 0、1、3、5 秒的位置与血量
- 双方基地、前哨站血量和剩余金币
- 目标机器人的速度、朝向、弹药变化、易伤状态和类型
- 当前比赛进度

比赛进度固定按规则时长 420 秒计算，不使用赛后才知道的实际结束时间。

蓝方样本会旋转 180° 到红方视角，因此模型学习的是阵营无关的战术规律。训练、验证、测试按整场比赛分组；同一场 BO3/BO5 的不同局不会跨集合，避免测试分数虚高。

## 训练多峰时序 Transformer（当前默认）

模型把 `0 / -1 / -3 / -5` 秒的全场状态投影成 4 个战场 token，再加入 1 个目标机器人上下文 token，经过 3 层、4 头、270,824 参数的 Transformer Encoder，为未来 `1 / 3 / 5 / 10 / 15` 秒分别输出 8 个二维高斯分量。上下文包含目标队伍、对手队伍和最近 1/3/5 秒受击量，因此能区分各队在受击前后的部署变化。监督目标只有真实未来坐标，损失中没有“近战/远程/架点”等人工阈值标签。它是 PyTorch `nn.TransformerEncoder` 的真实多头自注意力训练，不是把 MLP 改名，也不是大语言模型。

```bash
# 先复现单点基线，再训练与它盲测对比的多峰候选
python3 ml/train_trajectory_transformer.py
python3 ml/train_trajectory_mixture_transformer.py
python3 ml/audit_trajectory_mixture_conditioning.py
python3 ml/export_browser_transformer.py
```

默认用全部 613 局，按系列赛隔离为 431 / 94 / 88 局，最多取 30 万训练样本。开发期冒烟测试曾查看旧测试集前 8 局，因此正式验收会把这 8 局涉及的 4 个完整系列赛、共 9 局全部排除，最终盲测使用剩余 79 局；同一场 BO3/BO5 不会一部分用于开发、一部分冒充盲测。输出为：

```text
ml/artifacts/trajectory_transformer.pt
ml/artifacts/trajectory_transformer.metrics.json
ml/artifacts/trajectory_mixture_transformer.pt
ml/artifacts/trajectory_mixture_transformer.metrics.json
ml/artifacts/trajectory_mixture_transformer.conditioning_audit.json
docs/data/models/trajectory_transformer.json
docs/data/models/trajectory_transformer.bin
```

多峰模型不删除静止样本，也不按人工风格重标数据；训练集中的每个目标仍是裁判轨迹里的精确坐标。单点基线保留原有采样权重，用于检验多峰模型是否真的改善不确定性，而不是只和弱基线比较。快速验证命令：

```bash
python3 ml/train_trajectory_mixture_transformer.py \
  --epochs 2 \
  --max-games-per-split 10 \
  --max-train-samples 5000 \
  --max-val-samples 1000 \
  --max-test-samples 1000
```

正式训练不要设置 `--max-games-per-split`。发布门禁要求测试集整体、英雄和近期受击英雄的概率分布指标超过校准后的单点 Transformer；不通过时脚本直接报错且不发布检查点。训练完成后必须执行导出脚本，并运行 `python3 -m unittest ml.test_trajectory_transformer` 验证浏览器 JavaScript 的 logits、均值和尺度与 PyTorch 推理数值一致。

在项目根目录运行：


```text
ml/artifacts/trajectory_mlp.pt

```

快速验证数据管道可以缩小样本和轮数：

```bash
python3 ml/train_trajectory.py \
  --epochs 2 \
  --max-train-samples 20000 \
  --max-val-samples 5000 \
  --max-test-samples 5000
```

报告会把模型与两个基线比较：

- `stationary`：假设机器人停在原地
- `constant_velocity`：按最近 3 秒速度直线外推
- `learned_mlp`：本模型

位置误差之外，`zone_accuracy` 把 28 m × 15 m 场地划成 4 m × 3 m 的战术格，衡量“下一步会去哪一片区域”。

## 当前多峰 Transformer 结果

当前检查点在未参与梯度更新和早停的比赛分组盲测集上评估 60,249 条轨迹，其中英雄 10,241 条、近期受击英雄 684 条。概率分布使用 proper scoring rule 评估，不允许看见答案后挑最近的分量：

- 全体轨迹能量分数：单点校准基线 `1.181796 m`，多峰模型 `0.941755 m`
- 英雄 10 秒能量分数：单点校准基线 `1.873956 m`，多峰模型 `1.428853 m`
- 近期受击英雄 10 秒能量分数：单点校准基线 `2.429611 m`，多峰模型 `2.064515 m`
- 五项发布门禁全部通过；完整盲测分组清单和 NLL 见 `artifacts/trajectory_mixture_transformer.metrics.json`

冻结权重后又在同一预留盲测分组做了反事实消融，不再训练或调阈值：打乱队伍身份会让英雄 NLL 变差 `0.105787`，删除近期受击会让受击英雄 NLL 变差 `0.024668`，把场上血量或比赛时间替换为训练均值也分别变差 `0.030494 / 0.004773`。这说明队伍身份、受击、双方实时血量和时间不只是列在输入表里，冻结模型确实使用了它们。完整报告见 `artifacts/trajectory_mixture_transformer.conditioning_audit.json`。
- 冻结模型的反事实审计中，英雄使用正确学校身份的 NLL 为 `-4.682062`，仅替换成错误学校后退化为 `-4.576279`；53 支英雄样本不少于 100 条的盲测队伍中，`83.02%` 使用正确身份更好
- 684 条近期受击英雄样本中，保留真实受击特征的 NLL 为 `-3.560326`，仅抹掉受击特征后退化为 `-3.535654`；该审计不参与训练和调参

## 远程英雄部署 Transformer

`train_hero_deployment_transformer.py` 是独立的真实多头时序 Transformer，不用“远程英雄通常静止”之类伪标签。区域赛导出没有部署开关，因此状态监督只取能唯一判定的基地 42mm 事件：完整排除大能量机关激活后最长 60 秒污染窗和所有飞镖事件后，单发 300 是部署正例，单发 200 是机动负例。退出头只在已由精确 300 事件确认的部署片段上训练，标签是随后 2–10 秒内底盘是否离开确认点至少 0.45m；输入同时含最近四帧位置、1/3 秒速度、1 秒掉血与发弹、双方基地/前哨/地面总血量、最近敌车、金币、时间、队伍和对手身份。

```bash
python3 ml/train_hero_deployment_transformer.py
python3 ml/build_full_simulation_data.py
python3 -m unittest ml.test_hero_deployment_transformer
```

当前按系列赛隔离的盲测集中，部署状态有 1,195 条样本，ROC AUC 为 `1.0000`；退出头有 1,177 条已确认部署样本，其中 20 条退出、1,157 条保持，ROC AUC 为 `0.7319`。类别极不平衡，所以发布门禁检查排序 AUC 和正负样本覆盖，不用“全预测保持”得到的 98% 假准确率冒充效果。浏览器 JavaScript 前向与 PyTorch 导出探针的两个概率误差均小于 `1e-6`。

运行时只允许远程整机在真实部署区进入部署；部署期间路线和目标点锁在当前位置，底盘禁止移动。退出被触发后继续锁死整整 2 秒，再恢复机动。普通 42mm 始终为 200，部署命中基地才为 300；飞镖 200/300/625/1000 继续走独立结算。受击通过掉血时序进入退出头，不在引擎里按学校名特判；像同济这类真实片段几乎都为保持的队伍，不再被旧的“缺弹立即回补”规则强制反复离开吊射点。

## 英雄真实发弹阵位排序

`train_hero_firing_ranker.py` 不训练“近战/远程”推断标签。每个训练组把英雄下一次实际发射 42mm 时的位置作为唯一正例，另外三个候选也必须是比赛中真实出现过的发弹阵位：优先取同队同阶段阵位，不足时才取同队相邻阶段或同阶段其他队阵位。输入包含比赛时间、英雄当前血量与近 5 秒受击、双方基地/前哨血量、双方地面存活与总血量、金币、易伤状态、候选坐标及其到双方建筑和最近敌车的距离；明确排除“当前位置到候选的距离”、英雄整机类型和推断的近远程风格，防止模型靠“下一发通常离当前位置最近”或伪标签取得虚高分数。

```bash
python3 ml/train_hero_firing_ranker.py
python3 ml/build_full_simulation_data.py
python3 -m unittest ml.test_hero_firing_ranker ml.test_full_match_transformer_policy
```

默认按系列赛隔离后的测试集有 5,646 个四选一组：Top-1 为 `54.69%`，只用训练系列赛热图的基线为 `50.20%`，随机基线为 `25%`，两两排序准确率为 `69.55%`。另外用 7803–7806 四个划分种子分别从头训练，22,080 组加权 Top-1 为 `57.08%`，对应热图基线 `52.73%`，44 队都至少一次出现在某次留出测试中。不同次重采样的测试系列赛可能重叠，所以这不能冒充四折互斥交叉验证；完整口径见 `artifacts/hero_firing_ranker.multisplit.json`。

这个提升有限，说明现有区域赛事件足以学到一部分“血量/时间/战损/建筑状态下选哪个真实阵位”，但不足以声称模型已经还原完整指挥决策。运行时它只给合法真实候选加分，射程、视线、地形和补给仍是硬约束；轨迹时序由上面的真实多头 Transformer 提供，阵位排序器本身是更适合该四选一表格任务的残差排序网络，不冒充 Transformer。

## 调用模型

指定一局和一个时刻，可以预测当时场上所有移动机器人：

```bash
python3 ml/predict_trajectory.py --game-id 1780037479635 --second 200
```

也可以只看一辆车：

```bash
python3 ml/predict_trajectory.py \
  --game-id 1780037479635 \
  --second 200 \
  --side 红 \
  --robot-type 哨兵
```

如果预测时刻之后的真实帧仍在该局数据中，输出会一并给出真实坐标和误差，便于回放对照。

这还是行为预测模型，不是可做反事实推演的完整环境。后续要训练决策策略，应先在它之上增加事件/伤害预测、资源状态转移和不确定性分支，再做离线模仿学习或保守离线强化学习。

## 完整机器人沙盘与快速对局模拟

独立页面 `docs/simulator.html` 的“对局模拟”顶部是逐机器人完整沙盘。它先以 1 秒为步长生成 421 帧状态，再像比赛录像一样播放。沙盘同时维护双方英雄、工程、两台步兵、哨兵和空中的：

> 准确性边界：完整沙盘不是大语言模型，也不是无约束的端到端强化学习。`trajectory_mixture_transformer.pt` 的 10 秒八分量分布只作为候选倾向；英雄阵位排序器再根据本车和双方地面总血量、近 5 秒受击、存活数、剩余时间、金币与建筑血量，对真实发弹热区候选重排。已确认的前哨任务、补给、科技核心、地形门禁、伤害、复活和基地护甲仍由数据标签与 V2.1.0 规则约束。

- 坐标、地形约束路线、目标点、枪口朝向和碰撞间距；
- 当前/上限血量、等级成长、战亡读条、复活无敌和虚弱状态；
- 17mm/42mm 允许发弹量、射击热量、冷却、发弹与命中；
- 三类补给判定：基地区和前哨站下只补弹，补给区可补弹并回血；按 V2.1.0，读条复活后的虚弱可在三处交互点解除；
- V2.1.0 英雄“近战优先/远程优先”10 级血量表；默认整机类型按队伍统计画像推断并可由页面覆盖，但该画像只决定规则血量表和用于解释展示，不作为英雄阵位排序器的风格标签或选点阈值；
- 基地护甲按 V2.1.0 独立维护闭合/展开状态：180 秒后且前哨已毁，敌方连续占领堡垒 20 秒才开甲；闭甲时 17mm 上方前装甲为 5 点，42mm 为 200 点；基地飞镖只会生成 200/300/625/1000 四种规则伤害；
- 原地读条与立即买活决策：读条、买活价格、10%/100%复活血量、无敌/虚弱时间均按 V2.1.0 逐秒计算；
- 无人机使用独立的停机坪→起飞→巡航→返航状态机：初始 30 秒免费支援、每分钟累积 20 秒，耗尽后可按 1 金币/秒继续；普通伤害、地面补给、战亡和复活对它均不适用；
- 每队雷达能力由区域赛反制事件统计；空中最多被反制 5 次、每次只锁定发射机构 45 秒，不会被击毁或强制降落，第 4/5 次可以双倍金币解除；
- 工程卡片、机器人详情和地图装配区同步显示已兑科技核心 Lv.0-Lv.4、下一等级计划、当前每 10 秒核心经济和累计产金；
- 公路隧道与高地隧道使用严格二元能力门禁：对每个学校×具体兵种×隧道类型分别统计，样本中至少完整穿越 1 次才判定会过，从未穿越则直接作为训练负标签并强制绕行；人工确认/排除仍可覆盖轨迹噪声；
- 已标注地形使用“规划层+执行层”双门禁：局部绕行失败时不得回退为直线穿越，逐秒移动和机器人碰撞分离后也再检查一次；
- 前哨站被击毁后立即关闭“前哨站下”的补弹和虚弱解除交互，机器人会重新选择基地或补给区；
- 地面机器人按地面层/中央高地层/梯形高地层判定射界：弹道横穿整块高地会被阻断，但允许从地面攻击高地边缘的前哨站；空中机器人不受该高度层遮挡；
- 工程在己方装配区内按全局累计获得 180 秒无敌，离开区域时暂停计时，耗尽后不再生效；无敌期间即使残血/虚弱也优先留在装配区，不强制撤回补给区，无敌耗尽后恢复正常补给决策；
- 地形通过不再沿用平地速度：中央/公路/梯形台阶分别计算上行和下行，43°坡、400mm 跳跃、飞坡、起伏路和隧道也有独立倍率；B3/R3 二级台阶还会从“台阶跨越”轨迹学习直行概率和横向偏移，上下台阶保留更长的低侧接近段，登上后的终止点/下台前的起始点向地图横向中心内收；
- 国赛双方固定以 400 金币开局，定时金币与 V2.1.0 一致。区域赛“队伍总金币”只用于学习每队科技核心的到达等级概率和首兑时刻，不把区域赛项目评级造成的初始金币差带入国赛；
- 科技核心必须由存活工程进入中央装配区才能完成，一级至四级首次经济为每 10 秒 +50/+25/+25/+50；二至四级的等级上限、防御和四级基地 +2000 血量随兑换逐秒生效；
- 默认按真实 1 秒播放，支持 0.5×、0.75×、1×、1.2×、1.5×、2×，并可逐秒前后检查；

### 怎么训练和修正沙盘行为

不要直接改 `docs/data/models/*.json`，它们都是构建产物。正确的分层是：

- **硬约束**：场地实体边界、规则伤害和哪些兵种有资格通过，分别在 `analysis/terrain_crossing_points.py`、`ml/export_browser_navigation.py` 和规则模型中维护，不交给概率模型违反。
- **地形能力标签**：`analysis/manual_terrain_capabilities.csv` 只写“某校×某兵种会/不会过”的人工监督标签；其余样本由完整穿越轨迹自动标注。
- **队伍行为标签**：`analysis/manual_team_behavior_labels.csv` 用于数据没有显式字段的监督信息，例如英雄整机类型、描述性的远/近程画像、确认的前哨任务角色。未人工标注的英雄仍会逐队计算结构距离、最近敌车距离、远距发弹占比和连续发弹驻点率；这些画像不进入英雄阵位排序网络，也不控制其实时选点。队名只出现在模型身份输入中，不得在 JS 引擎写 `if (队名)` 特判。
- **44 队覆盖门禁**：每次构建后测试会验证 44/44 都拥有上述画像与地形动作模型，并检查运行时引擎不包含任何学校名。当前 44 队行为签名全部不同；样本不足只能在单个维度上回退，不会把整支队替换成统一模板。
- **可学习过程**：`ml/train_terrain_motion_profiles.py` 从裁判“飞坡”事件前后的 1 Hz 轨迹学习每校×兵种的直线助跑距离、对位概率、停顿概率/时长和三段加速曲线；助跑距离取终点为飞坡事件时刻的最后一个轨迹位移段并限制在 1.0–2.8 m。同时检测完整从一侧穿到另一侧的 B3/R3 轨迹，将上台阶和下台阶分开学习入射偏角、横向偏移和直行概率。单个方向的样本少于 5 次时才回退到该方向的全局分布。
- **路径形状约束**：B1/R1 只能沿飞坡通道中心线通过，正飞坡和有反飞坡证据的兵种都按“助跑点→坡口中心→出口中心”生成共线航点；确认能直接跃上中央高地的兵种也必须沿所选边界的法线完成“直线助跑→坡唇→落点”。这些几何参数导出到 `terrain_navigation.json` 的 `routing.terrain_route_profiles`，快速宏观预测和完整沙盘共用同一个 `terrain-router.js`。
- **补给撤退**：补弹不再按直线距离选择基地/前哨/补给区，而是比较实际可达路线长度；补给区使用整块矩形，基地区在椭圆范围内避开中心随机取点，前哨只允许沿红蓝对攻轴朝对方基地一侧的半椭圆，不朝中央高地。直达失败时先撤到己方半场中继点再规划第二段。若当前位置与己方区域在已确认能力图中确实不连通，模型不会再假装“正在回补给”却原地等待，而会就地转点 3 秒后重试。对应策略参数也在 `routing.terrain_route_profiles.service_return`。
- **火力概率**：逐队发弹数与对手受击事件生成 `accuracy_models`；每局先在该队区间内抽样基础命中率，每一发再做伯努利随机判定。普通英雄 42mm 固定为 200；基地 300 必须由部署状态或大能量机关等独立状态产生，不能把混合事件的 300 主模态反向写成普通弹丸伤害。
- **基地伤害时序**：`base_damage_timing` 对 44 队分别统计直射、飞镖和全来源的 15 秒产伤窗。运行时只用直射强度调节合法射程/视线内的基地选目标权重，用飞镖强度调节规则允许的飞镖窗口；不会按统计值直接扣血。
- **实时目标分类**：`train_target_selection_model.py` 用同局同秒同口径的发弹角色占比归因受击目标，并训练“地面/前哨/基地”三分类器。它显式读取双方地面总血量、存活数、低血量车比例、本车血量/近期受击和剩余时间。界面逐车显示当前三个概率；前哨已毁时仍由硬约束把前哨概率归零。
- **英雄真实发弹阵位排序**：`train_hero_firing_ranker.py` 以实际下一发 42mm 所在位置对三个真实备选阵位做四选一监督；只用训练系列赛生成热图先验，验证/测试按系列赛隔离。当前点到候选点的距离、整机类型和近远程画像全部排除，网页前向结果由 `test_hero_firing_ranker.py` 与导出权重逐项核对。
- **远程英雄部署**：`train_hero_deployment_transformer.py` 用排除大能量机关污染窗后的基地 42mm 200/300 精确标签训练机动/部署状态，再从已确认部署片段的真实后续位移训练保持/退出。部署不可移动、退出延迟 2 秒和普通/部署伤害 200/300 是物理规则，不让概率模型近似。
- **混合战术选点**：Transformer 不再压成单坐标直接接管机器人。引擎先收集当前分钟的该校×兵种热区、当前附近的真实 5 秒转移终点和规则候选，再按八分量概率密度、局势特征、目标分类概率、射程与视线共同重排。这样保留宏观热区形状，也不会把两个有效战术点平均成空地；受击量和队伍身份都来自模型输入，不在 JS 中写学校名特判。

`manual_terrain_capabilities.csv` 的 `ability` 可填 `central_highland_step`、`road_step`、`fly_ramp`、`rough_road`、`road_tunnel`、`highland_tunnel`、`slope_43`、`trapezoid_highland_step` 或 `central_highland_400mm_jump`，`label` 只能是 `confirmed` / `rejected`。`manual_team_behavior_labels.csv` 当前支持 `outpost_assault_role`、`hero_archetype_default`、`engagement_style` 和 `deployed_base_damage_per_hit`。每次改 CSV 后都必须重新运行下面的构建链。

完整重训顺序：

```bash
python3 analysis/team_terrain_capabilities.py
python3 ml/train_terrain_motion_profiles.py
python3 ml/export_browser_navigation.py
python3 ml/train_target_selection_model.py
python3 ml/train_hero_firing_ranker.py
python3 ml/train_hero_deployment_transformer.py
python3 ml/build_full_simulation_data.py
python3 -m unittest analysis.test_team_terrain_capabilities ml.test_browser_navigation ml.test_hero_firing_ranker ml.test_hero_deployment_transformer ml.test_match_simulator
```

想加新的跨地形属性时，先在 `terrain_crossing_points.py` 定义几何门，再在 `team_terrain_capabilities.py` 定义正负样本口径；如果它还包含“直线助跑→对位→停顿→加速→落地”时序或“入射角→横向漂移”轨迹特征，再给 `train_terrain_motion_profiles.py` 增加事件窗口，最后由 `export_browser_navigation.py` 导出到浏览器模型。中心线、边界法线等不能被概率违反的条件放进 `terrain_route_profiles`；从轨迹能估计的距离、概率和速度放进每校×兵种的 `terrain_motion_profiles`。

### 快速宏观推演

上方完整沙盘与下方快速推演共用红蓝学校选择，任一处修改都会同步另一处并重开对应推演。快速模型同样维护基地护甲状态，闭甲阶段不会把 15 秒历史混合火力整段当作满额基地伤害；飞镖的连续混合值会还原为基地 200/300/625/1000 或前哨 750 的离散单发伤害，并把档位写入回合日志。

独立模拟页下方的快速宏观推演把一局 420 秒切成 28 个 15 秒回合。每队每个回合会从真实比赛样本中抽取并融合：

- 基地、前哨站和地面机器人的伤害；
- 17mm、42mm 与飞镖伤害构成；
- 飞镖命中/开闸窗口；
- 己方与敌方堡垒附近的驻留时间；
- 能量机关增益和官方记录的地形动作。

网页默认展示 TDT 对 RPS，可逐回合落子、自动演算单局，或批量模拟 500 局。跨赛区对阵属于反事实推演，批量结果是用于比较战术风格的实验分布，不是官方胜率。

战队热图位于完全独立的 `docs/heatmap.html`，不复用单场比赛回放的地图、时间轴或状态。它覆盖区域赛 96 支学校，可切换位置、打弹、受击、击杀和阵亡五类热力图：位置来自 1Hz 存活机器人轨迹；发弹和受击按数据库事件的同局、同秒、同 `robot_id` 映射机器人位置，仅有缺帧时才取相邻 1 秒轨迹；阵亡在同一 `robot_id` 的血量由正数首次转为 0 时记录归零当秒坐标；击杀只统计敌方归零秒或前 1 秒存在 17mm/42mm 受击证据的记录，并归到对手学校。裁判数据没有具体击杀者，因此击杀模式的兵种筛选表示被击杀兵种。五种模式都用 280×150 的等物理尺度网格表达 28×15m 裁判坐标域（每格 0.1m），显示时将其嵌入 29×16m 整图，四边各留 0.5m，再以 σ=0.22m 的二维高斯核展开单点误差。学校下拉框除 96 支单校和预聚合的“全部学校（96队）”外，每个赛区还提供该赛区 32 队的预聚合全选项，因此按赛区或兵种查看整体分布时都不需要浏览器临时下载并相加多份数据。数据按比赛进程聚合为 28 个连续的 15 秒窗口，可播放、拖动和逐段查看；支持双边原位、统一红方和统一蓝方三种视角。重新生成热图数据：

## 操作手战术推理

`tactical_inference.py` 把坐标预测转成客户端可直接显示的内容：

- 5/10/15 秒候选战术区域，10 秒为主目标；
- 预计经过的 B/R 地形入口和路线摘要；
- 对照人工确认/官方事件/轨迹证据的能力风险提示；
- 全场状态模型与 44 队的学校×兵种×区域×比赛阶段先验融合。

构建/更新战队先验：

```bash
python3 ml/build_tactical_priors.py
```

回放某一时刻的操作手输出：

```bash
python3 ml/tactical_inference.py \
  --game-id 1778680444314 --second 200 \
  --side 红 --robot-type 步兵3
```

本地 HTTP 服务：

```bash
python3 ml/tactical_api.py --host 127.0.0.1 --port 8765
```

`POST /infer` 只需提供当前 `second`、红蓝学校信息和最近 5 秒帧。帧内每个机器人使用导出数据的紧凑数组格式：

```text
[id,type,side,hp,max_hp,x,y,yaw,ammo17,ammo42,coins,vulnerable]
```

推理器使用 MC dropout 生成候选分布；`display_confidence` 还会乘以独立测试集在对应时距上的历史战术格命中率。它适合做提示强度，不应解释为严格的贝叶斯概率。
